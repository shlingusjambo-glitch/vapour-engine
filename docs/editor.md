# The Vapour editor

The editor is a browser application. It opens a project, edits its scenes, and
writes changes back to the project folder — nothing is stored in a proprietary
database, and every file it writes is text you can read in a diff.

## Layout

| Region | Purpose |
| --- | --- |
| Menu bar | File, Edit, GameObject, Component, and View commands. Items grey out when they cannot run. |
| Toolbar | Transform tools, gizmo space, snapping, play controls, renderer tier. |
| Hierarchy | The scene tree. Search, multi-select, collapse, and drag-to-parent. |
| Scene view | The WebGPU viewport with navigation, selection, and gizmos. |
| Game view | The same scene through the authored `vapour.Camera`, as a player sees it. |
| Inspector | The selected entity's name, enabled flag, Transform, and components. |
| Assets / Console / Profiler | Project files, engine messages, and live frame statistics. |

## Navigating the Scene view

| Input | Action |
| --- | --- |
| Alt + drag, or right-drag | Orbit around the pivot |
| Middle-drag, or Alt + Shift + drag | Pan the pivot |
| Wheel | Zoom toward or away from the pivot |
| `F` | Frame the selection, or the whole scene when nothing is selected |
| Double-click a hierarchy row | Frame that entity |
| View → Reset Scene Camera | Return to the default view |

The Scene view has its own camera. Navigating never moves the game's camera and
never marks the scene as modified — the two are separate on purpose, so you can
look wherever you like without disturbing what ships.

## Selecting

Click an object in the viewport to select it. Selection is a real ray cast
against the geometry the renderer drew, so what you click is what you get.
Shift-click or Ctrl-click adds to and removes from the selection, in the
viewport and in the hierarchy alike.

With several entities selected, the inspector edits the **last** one selected
while Duplicate, Delete, and Move To Scene Root apply to all of them.

## Transform tools

| Key | Tool |
| --- | --- |
| `Q` | Select |
| `W` | Move |
| `E` | Rotate |
| `R` | Scale |

Drag a coloured handle to transform along that axis. The gizmo is drawn with the
same camera the renderer used, so handles sit exactly where the geometry is.

**Gizmo space.** The `LOCAL` / `WORLD` toggle switches between the entity's own
axes and world axes for Move and Rotate. Scale is always local and the toggle
disables itself: a per-entity scale vector cannot express stretching along a
world axis, so offering the choice would be a lie.

**Snapping.** With `SNAP` on, moving and scaling advance in whole `STEP`
increments and rotating advances in whole `ANGLE` increments. Snapping is
incremental rather than absolute — a drag steps forward from where the object
already was, which preserves exact relative spacing.

**Child entities.** Transforms are stored in parent space. Dragging a world-axis
handle on a child converts the movement back through the parent's basis, so the
object follows the cursor rather than the parent's rotation.

## Built-in meshes

Seven primitives are generated by the engine rather than loaded from files:
cube, sphere, capsule, cylinder, cone, plane, and quad. **Every one fits inside
the unit cube**, so a Transform scale of 1 always means one world unit and
swapping a cube for a sphere never changes an object's footprint. An object
placed at `y = 0.5` sits exactly on a ground plane at `y = 0`, whichever mesh
it uses.

Instances that share a mesh are drawn in a single instanced call, so a scene
with a thousand cubes and a thousand spheres costs two draws, not two thousand.
The Profiler's draw-call count reflects this directly.

Selection and camera framing use each mesh's own extents: a capsule is narrower
than a cube, and a plane frames tightly instead of as if it were a box. Picking
is bounds-accurate rather than triangle-accurate — clicking the corner of a
sphere's box selects it — which keeps selection instant and needs no GPU
readback.

## Editing components

The Inspector shows Transform first, then every other component on the entity.
Rotation is shown in degrees; scenes store quaternions, and the editor converts
in both directions using the intrinsic Y→X→Z order that Unity and Godot display.

Every other component's controls are generated from its schema. There is no
hand-written panel for any component — which is exactly why a plugin component
gets a working inspector the moment it registers a schema. See
[plugins.md](plugins.md).

- **Add Component** lists only components the entity does not already have, and
  the list is searchable.
- **✕** on a component header removes it. Removal is undoable and restores the
  component's edited values, not its defaults.
- Colours are stored linear and shown through the browser's sRGB picker; the
  editor converts, so what you pick is what renders.
- A component with no registered schema — usually from a plugin that is not
  loaded — is shown as read-only and its data is preserved untouched on save.
  Vapour never silently drops scene data it does not recognise.

## Undo

`Ctrl+Z` and `Ctrl+Y` (or `Ctrl+Shift+Z`) walk the history. A continuous
gesture is one entry: dragging a gizmo across a hundred frames undoes in a
single press, back to where the drag started.

Undo covers entity creation and deletion, duplication, reparenting, renaming,
enabling and disabling, transform edits, component add and remove, and component
field edits.

## Saving

`Ctrl+S` writes the scene to the project. The editor also autosaves every 15
seconds while there are unsaved changes, and keeps a recovery copy in browser
storage so a crashed or closed tab does not lose work. The save indicator in the
menu bar reads `SAVED`, `UNSAVED`, `AUTOSAVED`, or `ERROR` — it never claims a
save that failed.

Scenes serialize with sorted entities and sorted components, so the same scene
always produces the same bytes and diffs stay readable.

## Appearance

The editor ships a dark theme by default and a light theme that matches the Hub;
View → Toggle Theme switches. The choice is stored per device and never enters
project data, so it cannot cause a diff.

Both themes are built from one set of tokens defined in
`packages/editor/src/style.css`. The design language is deliberately narrow:
a sans typeface for reading and a monospace one for every label and numeric
field, hairline borders instead of shadows, 4px and 6px radii, and a single
chromatic accent reserved for selection, focus, and the active tool.

## Current limits

These are real gaps, not oversights, and the editor does not pretend otherwise:

- The Mesh dropdown lists the seven generated built-ins. Importing meshes from
  glTF or any other format is not implemented, so nothing else can appear there
  yet.
- Materials are per-entity fields on the Mesh Renderer, not shared assets. Two
  objects cannot yet reference one material and change together, and there is
  no texture support: base colour, metallic, roughness, and emission are
  uniform across a surface.
- Vertex snapping is not implemented; the toolbar does not offer it.
- Multi-entity inspector editing changes the primary selection only.
- The Game view renders through the authored camera but does not yet run
  gameplay scripts or physics; the play controls change what the viewport shows.

Capability status for the whole engine is tracked in [status.md](status.md).
